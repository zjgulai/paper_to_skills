## 一、为什么还需要第三个扫描器：一条**实测**出来的缝

本仓库原有两套凭证口径，覆盖的是同一件事的两个切片：

| 脚本 | 看哪里 | 问什么 |
|------|--------|--------|
| `scan_secrets.py` | **已 tracked 文件的内容** | 现在入库的东西里有没有凭证 |
| `check_key_exposure.py` | **工作区的路径** | 有没有「未跟踪但也**未忽略**」的密钥 |

两者都只看**此刻**。构造样本实测（可复跑）：

```
$ git ls-files                       # 工作区：干净
README.md
$ git cat-file -s <blob>; git cat-file -p <blob> | head -1
111
<PEM 私钥头（此处刻意不写字面量，理由见 .gitignore 同名约定）>
$ python3 scan_secrets.py --root $T
扫描 1 个文件（文本 1 / 二进制 0），规则 13 条
✅ 未发现凭证                                   exit=0
$ python3 check_key_exposure.py --check --root $T
✅ 暴露面判据全过（工作区里没有被跟踪的密钥，也没有「未忽略」的密钥）   exit=0
```

**私钥没有被删除，只是不再出现在任何人的视野里。** `git push` 会把它一并推到远端，
`git cat-file` 一行就能取回。

> 这是本轮那句自检口令的第三次变体：
> **「我这一侧的读数，凭什么是对象那一侧的事实？」**
> 交付≠接线 · 自述≠指纹 · 能扫到≠一共有 · 没入库≠安全 · **工作区里没有 ≠ 仓库里没有**

## 二、三条判据的分工（**不许互相顶账**）

新门禁 `paper2skills-skills/paper-维护/scripts/check_history_secrets.py`。

| 判据 | 覆盖 | **看不见** |
|------|------|-----------|
| **A 路径史** | 任何 ref 的历史上 `--diff-filter=A` 添加过密钥形态文件名（哪怕之后删了） | 把 key 粘进 `.html` / `.json` / 笔记本 |
| **B 对象内容** | 对象库里**任何** blob 的正文命中凭证规则 | 加过密／打包过的密钥；**被拆开的凭证**（§6） |
| **C 已知暴露值还原** | 相邻字符串字面量拼起来能否**还原**出登记在册的已知暴露值 | 未登记的值 |

三条**分开报**：只有 A 命中 ⇒ 历史上出现过密钥文件；只有 B 命中 ⇒ 密钥被写进了普通文件；
只有 C 命中 ⇒ 值被拆开过但可一行还原。**合并成一个数，就再也回答不了「是哪一种」。**

规则表 / 转义归一化 / 白名单 / 打码预览**全部 `import` 自 `scan_secrets.py`**，本文件不另写一份
（S12 风险 N2：同一个判据不许有两处实现）。

### 可达与不可达必须分开

- `REACHABLE`：从某个 ref 可达 ⇒ **会随 push 出去**，处置是 `git filter-repo` 重写历史。
- `DANGLING`：只在对象库里（reflog／stash 残骸、`reset --hard` 之后的旧提交）⇒ 不随 push 出去，
  但 `.git` 被拷走即复原，处置是 `git gc --prune=now`。

⚠️ `--check` 的判据主体是 REACHABLE（**跨克隆确定**）；DANGLING 是**本机事实**（新克隆没有它），
单独成段并注明。混成一个数就会造出一条「结果取决于谁在哪台机器上跑」的门禁 ——
`check_key_exposure.py` 已经踩过同一个坑（那条 `--sweep-roots` 因此刻意不进验收面）。

## 四、覆盖率是**一等输出**（「没测」不许伪装成「干净」）

| 读数 | 含义 |
|------|------|
| `blobs_scanned == 0` ⇒ **exit 2** | 走过对象却一个 blob 都没扫（全被大小阈值跳过／全是二进制）—— **这不是干净，是没测** |
| `commits == 0` ⇒ **exit 2** | 空仓库 |
| `blobs_skipped_big` | 超过 `--max-blob-bytes`（默认 8 MB）未做内容扫描。**必须打出来**；若其路径本就是密钥形态 ⇒ **判红** |
| `objects_unreadable` | `git cat-file` 报 `missing` 的对象数，如实计数 |
| `c_skipped_groups` / `c_skipped_literals` | 判据 C 跳过的字面量组（见 §8） |

⚠️ 用例 6 抓住过我自己的一个错误：`verdict()` 第一版写成
`blobs_scanned == 0 **and** blobs_binary == 0 **and** blobs == 0` ——
于是「有 blob 但一个都没扫」被判成了干净。**「我扫过」必须由「真的扫到内容的 blob 数」证明。**

## 六、⭐ 判据 C：真值仍然在对象库里，而且**其中一条是活的**

### 6.1 为什么会漏：固件机制本身

`scan_secrets.py` 的既有写法是**把真值拼出来**当自测固件（其 docstring 明说
「运行时构造出的样本仍然是真值」）。拆开只骗得过**模式扫描器** ——
骗不过任何一个读源码的人：一行 `+` 就能还原文。

于是出现一个反直觉后果：
**用来防泄露的固件机制，把真值以「一行可还原」的形式留在了公开仓库里，
而 `scan_secrets.py` 报「✅ 未发现凭证」——因为拆开了，它按定义看不见。**

实测（扫过全部 3634 个 blob）：

| 探针 | 命中 blob |
|------|----------|
| `sk-<key 值>`（带前缀的完整形态） | **0** ✅ |
| `<key 值>`（去掉 `sk-` 前缀） | 2 · `762c39f750a6`（旧版）与 `9ef9e6375470`（**HEAD 版本**） |
| 飞书 hook UUID | 1 · `9ef9e6375470`（**HEAD 版本**） |
| 墓碑 `***REMOVED-DEEPSEEK-KEY***` | 25（filter-repo 确实清过裸值） |

### 6.2 判据 C 怎么做的

登记表 `data/exposed-credential-registry.json` **只存 `len + sha256`，不存值**
（一张写着真凭证的登记表是第二份泄露源，也正是它要防的东西）。
判据把源码里**相邻的字符串字面量**按顺序拼起来（覆盖 `_fx(a, b)` 与 `a + b`），
对所有**跨边界窗口**取 sha256 比对 —— **相等即命中，零误报**（不是启发式）。

### 6.3 ⭐ 实测：那条 webhook **仍然有效**

照 `CLAUDE.md` 的既有先例（「实测 `GET api.deepseek.com/models` → HTTP 401」），
对凭证端点发**只读 GET** 判死活 —— 飞书 webhook 的 GET **不发送任何消息**。
**带反向控制**（造一个同形但不存在的 UUID）：

| 探针 | 读数 |
|------|------|
| 对照（全 0 UUID，不存在的 hook） | HTTP 200 · `code=19001` · `param invalid: incoming webhook access token invalid` |
| 现场（被暴露的那个） | HTTP 200 · `code=19002` · `params error, msg_type need` |

⇒ **令牌通过了校验，只是没带消息体** ⇒ **该 webhook 至今有效**。

这不是「未轮换（未知）」，是**实测仍然有效**：任何拿到这个公开仓库的人，
把三段拼起来就能往那个群里发消息。而 `scan_secrets.py` 对它报的是「✅ 未发现凭证」。

处置：**活凭证不许豁免**（见 §7）。这条门禁因此**保持判红**，
直到飞书后台轮换完成 —— 红在这里是对的，它对应一个真实的、有行动主的未闭环项。

### 6.4 我改了什么、什么改不了

| 动作 | 状态 |
|------|------|
| 把固件里的**真值**换成**同形假值** | ✅ 已做。先证明「值身份不产生检出能力」：规则是 `\bsk-[A-Za-z0-9_-]{20,}` 这种**形状**判据，同形假值与真值**逐字节等价**（换完 8 组用例全绿）。分工明确：**用例管形状，登记表管值** |

## 七、豁免规则：**仍然有效的凭证不许豁免**

判据 C 的豁免是**按值**（`sha256`）给的，且有一条不对称的硬规则：

> **`measured_status == "live"` 的条目，白名单里写了理由也不生效，门禁照红。**

理由：豁免的语义是「已知且**无可行动作**」；活凭证**有**可行动作（后台轮换），
把它豁免掉等于把一条真实暴露静默掉。反过来，**已失效且无可行动作**的条目可以豁免 ——
`DeepSeek key` 那条正是如此（值已 401，且它的可还原形态只存在于已推送的历史里，改源码不能让它消失）。

豁免每次运行都**逐条打印**理由与到期条件 —— 豁免是「可见」，不是「忘记」。
白名单条目**缺 `reason` / `expires_when` / `evidence` 任一 ⇒ 不登记且判红**。

本轮白名单 3 条：2 条 blob（两个扫描器自己的旧修订，全是占位值/固件）+
1 条 registry（已失效的 key）。**飞书 webhook 刻意不在表内。**

### 三个自抓的仪器缺陷（登记以示同族）

1. **变异锚点被变异表自己抄了一遍**（S11 的坑，`--mutate` 首跑就踩）：
   `MUTATIONS` 表里写的锚点字符串 `        found = SS.scan_text(text)` **本身**就是源码里的第二处出现
   ⇒ 锚点计数 2 ⇒ 变异施不上力。处置：锚点**拼**出来，并加「锚点在源码里恰好出现一次」的断言。
2. **同一判据两处实现 ⇒ 没有任何单点变异能改变行为**：白名单的「缺 reason 即无效」
   第一版写在两处（loader 标空 reason + 消费方 `bool(reason)`）⇒ M4 端到端**翻不了面**。
   这不只是可测性问题 —— 两处实现正是 S12 风险 N2（两边会各自漂移）。
   改为**只在 `load_whitelist` 判定一次**，无效条目不登记。
3. **性能缺陷**：判据 C 第一版对每个字面量组做 O(k²) 个候选、每个候选再拼一次中间段（实际 O(k³)）
   ⇒ 语料上实测 **9 s → 162 s**，直接超掉验收面能接受的时间。
   改为**按边界取窗**（值的长度是 n，跨过边界 b 就必然落在 `S[b-n+1 : b+n-1]` 里），
   **与组大小线性、与值长线性，且不漏**（跨 3 段以上的值照样落在某个边界窗里）⇒ 回到 16.6 s。
