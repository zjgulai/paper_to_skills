# FLOW-06 · 需求到数据产品与业务工具 · 方案域

> **这份文档是什么**：FLOW-06 这一格的**作业总图** —— 八个阶段怎么走、12 个岗位各贡献什么、
> 批次里那 37 份契约挂在哪、方法从哪些卡来、缺什么。
>
> **这份文档不是什么**：
> - 不是方案模板（真正的取值口径在契约里，逐责任的算式与冻结条件在那里）；
> - **不是喂给模型的资料**。F6/F7 两轮实测已证伪「契约/方案进提示词能提升产出」：
>   契约臂的量化判据中位数 3（对照 19.5 / 单卡 22），削到只剩取值仍只有单卡臂的 47%。
>   ⇒ 本层是**人的标定物**与**消费口闸门条件**（S12），不是载荷。
> - 不是成品方案 —— 它给的是**作业面**；具体一次 Case 的需求契约与工具交付包由主岗位产出。

## 2 八阶段作业总图

格类型决定了**每一格允许挂什么**：`M` = 算法模型接入点（A/B 类责任的方法与标定取值落在这里）；
`R` = 判据与契约（模型只做有界分类，**不得作主引擎**）；`D` = 无模型参与，不消耗检索预算（风险 N4）。
「标准产物」一列**逐字**取自图谱的 `business_output_name`，写契约时不许改写名字。

| STG | 阶段 | 格 | 业务步骤 | 标准产物（逐字） | 本格挂什么 |
|---|---|---|---|---|---|
| STG-01 | 信号接收 | `D` | 接收真实业务能力需求或数据错误 | **数据与工具需求信号** | 只落判据：什么算「真实业务任务」、什么算重复需求、数据错误的严重度分档（**不接算法**） |
| STG-02 | 范围确定与Case创建 | `R` | 确定业务任务、对象、现有方法、优先级、约束和验收结果 | **能力交付Case Charter** | 契约与判据为主：对象与现有方法是否指名、验收结果是否可判定、优先级冲突须 WAIT/FREEZE |

| STG-05 | 方案与标准产物 | `M` | 形成需求契约、数据契约或工具交付方案 | **数据/工具交付包** | **算法接入**：指标契约与数据契约生成 · 管道编排 · 工具实现与回归 · 知识/技能版本 |

| STG-08 | 结果核验、关闭与异步学习 | `M` | 核对业务验收、质量、运行结果并发出异步学习候选 | **能力交付关闭记录** | **算法接入**：验收核对 · 质量回归 · 运行结果对账 · 经验→能力版本的候选生成 |

### 2.1 一条 Case 的走法（把上表连起来）

```
需求信号 / 数据错误(D)：区分「真实业务任务」与重复需求
  → 能力交付Case Charter(R)：定对象、现有方法与耗时、输入与标准产物、优先级理由与约束
  → Context Manifest(D)：Case Agent 依次加载 AGT-045 口径 → AGT-046 数据质量 → AGT-047 工具交付
       → AGT-050 访问边界 → AGT-049 运行恢复 → AGT-048 能力治理（PB-006「步骤」段逐字）
  → 能力缺口诊断(M)：业务语义 / 对象映射 / 数据来源与质量 / 现有系统 / 复用可能
  → 数据/工具交付包(M)：需求契约 + 数据契约 + 工具交付方案
  → Assurance(R)：Access / 数据质量 / 运行恢复 / 安全 / 经营验收设计 五项 → HOLD 或放行
  → 受控动作(D)：发布 Change Proposal 或 NoActionRecord；Bundle 变更走 D-023 生命周期
  → 关闭与学习(M)：业务验收、质量、运行结果 → 《能力交付关闭记录》+ 异步学习候选
```

**三条不许绕过的规矩**（材料原文口径）：

1. **缺关键输入时进入等待或自治异常，不把缺失值当作零**（`PLAYBOOKS.md` §通用工单规则）。
2. **新工具失败时恢复已知可用流程，保留影响范围，不重写原始事实凑齐报表**（`PB-006` 异常与恢复段）。
   —— 这条是本条 FLOW 的**身份条款**：一个「需求到数据产品」的流程如果把原始事实改了去凑报表，
   它交付的就不是能力而是假账。
3. **Bundle 变更只能走 D-023 生命周期**（`FLOW-06/STG-07` 原文「Bundle变更转入发布生命周期」；
   `FLOW-08/STG-07` 把同一个约束写得更直白：「Bundle只能走D-023生命周期」）。
   ⇒ **禁止**让一次工具交付包**直接**改动 Agent 的能力装配。

## 4 方法从哪来（卡 ↔ 契约）

**契约按「责任」建，不按「卡」建**：一个责任的同族方法卡可以互换，换卡只换方法实现，
数据要求、标定规则与冻结条件不变。因此每份契约的 `cards` 只写 1–3 张**代表卡**。

## 6 停止条件与冻结（本 FLOW 的判据面）

**STG-06 Assurance 接收门禁五项检查**（逐项可判定；缺项即 HOLD，不设「部分通过」档）：

1. **Access** —— 本次读取/写入是否落在被授权的账号、系统与数据范围内（AGT-050 的访问控制与授权审查）；
2. **数据质量** —— 输入数据的质量状态、来源与新鲜度是否支撑该交付（AGT-046）；
3. **运行恢复** —— 交付物失败时的恢复路径是否存在且被验证过（AGT-049 的失败恢复）；
4. **安全** —— 工具范围与发布动作是否触发安全事件边界（AGT-050）；
5. **经营验收设计** —— 验收是不是**可判定**的（不是「看起来好了」），且由工单定义的负责人与独立复核执行（`FLOW-CATALOG.md` §FLOW-06 逐字）。

**必须冻结／不得自动进入 STG-07 的情形**（`PB-006` 异常与恢复段逐字 + 各契约 §6 细化）：

- **语义争议** ⇒ 按**数据契约和口径策略**处理（不是按谁的声音大）；
- **技术故障** ⇒ 归入**工具异常**（不许混进「需求变更」重开 Case）；
- **优先级冲突** ⇒ 由 Case Control 按场景目标和**确定性规则**进入等待或冻结；
- **新工具失败** ⇒ 恢复**已知可用流程**，保留**影响范围**，**不重写原始事实凑齐报表**；
- **Bundle 变更** ⇒ 只能走 **D-023 生命周期**，不得由本 FLOW 直接改装配；
- 数据更新后原方案失效者，回 STG-04/05 重算，不得沿用旧取值。

> **D-026 紧急保护通道在本条 FLOW 不适用。** 它的入口在 `FLOW-07/STG-01`（「符合D-026候选条件时交由模型外
> Emergency Guard 评估」），本条的受控动作是 **Change Proposal**，不是紧急保护。
> 把 D-026 写进 FLOW-06 会让「发布一条管道」看起来像「紧急保护一个账号」——**门禁语义会被换掉**。

### 8.1 一条结构性发现：**有卡 ≠ 有方法可用**

- **每层判据只有一处**：责任名/岗位/域/面/flows/格 全部由 `capability-graph.json` 导出，
  契约 frontmatter 由生成器写、校验器独立重算比对（漂移即报错，不是「看起来一致」）。
- **方案层是派生不是手写**：`cells[].solution_refs` 由 `solutions/*.md` 算出 ——
  本文件一旦缺 `flow_id`，图谱**拒绝出图**（selftest 变异 B）。
