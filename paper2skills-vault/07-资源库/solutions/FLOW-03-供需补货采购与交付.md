# FLOW-03 · 供需补货采购与交付 · 方案域

> **这份文档是什么**：FLOW-03 这一格的**作业总图** —— 八个阶段怎么走、13 个岗位各贡献什么、
> 36 份契约挂在哪、方法从哪些卡来、缺什么、什么条件下不许自动走。
>
> **这份文档不是什么**：
> - 不是方案模板（真正的取值口径在 36 份契约里，逐责任的算式与冻结条件在那里）；
> - **不是喂给模型的资料**。F6/F7 两轮实测已证伪「契约/方案进提示词能提升产出」：
>   契约臂的量化判据中位数 3（对照 19.5 / 单卡 22），削到只剩取值仍只有单卡臂的 47%。
>   ⇒ 本层是**人的标定物**与**消费口闸门条件**（S12），不是载荷；
> - **不是成品方案** —— 它给的是**作业面**，具体一次 Case 的供应计划由主岗位 AGT-016 产出；
> - **不是 ERP 的替身**。材料的自治控制第一条就是 **系统-of-record**：
>   **「库存预留和采购承诺只复用业务系统权威记录与回执。」** 本层不持有库存，也不产生预留。

`R` = 判据与契约（模型只做有界分类，**不得作主引擎**）；`D` = 无模型参与，不消耗检索预算（风险 N4）。

> 🔢 **算出来的观察**：`8 FLOW × 8 STG = 64 格`，全局分型 **M 24 / R 16 / D 24**

### 2.1 一条 Case 的走法（把上表连起来）

```
库存/预测/交期/采购/履约变化(D) → 供需Case Charter：账号/SKU/仓库/供应商/时间窗/供需目标(R，零多匹配即 WAIT)
  → Context Manifest：钉唯一主岗位 AGT-016 与 Bundle，装配 13 个岗位里本次用到的那几个(D)
  → 诊断(M)：核对可售/预留/在途、已有订单、需求区间、交付周期、产能、条款、现金
             产出《供需证据与约束诊断》（**先核对对象与已有订单**）
  → 方案(M)：比较补货 / 调拨 / 控投放 / 清货四类方案，产出《供应计划与动作方案》
  → Assurance(R)：重复订单 / MOQ / 产能 / 现金 / 质量 / 合同 / 对象状态 七项检查 → HOLD 或放行
  → 受控动作(D)：仅提交策略允许的采购/调拨 Intent；无需动作时出 NoActionRecord
  → 关闭与学习(M)：订单→到货→质检→可售→结算→资金影响 串成同一业务事件，《供需关闭记录》
```

**四条不许绕过的规矩**（PB-003 原文口径）：

1. **先核对对象与已有订单，再比较方案**（PB-003 步骤第一句）——
   这是本 FLOW 特有的顺序约束：PB-001 与 PB-002 的步骤原文里**都没有**「先核对对象与已有订单」这一步（逐字比对）。
   **采购重复**正是它要防的失败模式（见 §7）。
2. **不得为完成补货任务而自行拆单绕过阈值**（PB-003 异常原文）。
   ⇒ MOQ/产能/现金约束不满足时，**回到方案阶段缩小或重组**，或冻结相关范围。
3. **取消和重下单前查核实际合同与履约状态**；已成功动作**不得随整单重跑**；回执不明时**先查实际效果**。
4. 每项记录随带**统计窗和新鲜度**；缺关键输入时进入等待或自治异常，**不把缺失值当作零**。

### 3.2 为什么是 36 而不是 40

13 个岗位共 **40 条 L3 责任**（AGT-002 有 4 条，其余各 3 条）：
**A 28 + B 8 = 36 条建契约**，另 **4 条是 C 类，不建契约** ——

`OEM协作`（AGT-014）· `仓储协作`（AGT-020）· `税务资料`（AGT-042）· `申报协作`（AGT-042）。

> ⚠️ **AGT-042 合账的 3 条责任里只有 1 条进契约**（实体口径核对），另两条（`税务资料`/`申报协作`）是 C 类。
> ⇒ 「这个岗位在本 FLOW 有几个贡献点」与「这个岗位有几条责任」**不是同一个数**。
> 这也是 `139 = 151 − 12` 在本 FLOW 的落点：**C 类不建契约是设计，不是遗漏** ——
> 「给 C 类建契约只会制造形式主义」（契约层 README §1）。

> 它在本 FLOW 的 1 份契约是 B 类 —— 它的责任要靠外部证据 + 替代路径讲清楚。

### 3.3 A/B 是材料 §F.3 的口径判定，不是本方案域的重判

> **A/B 逐条理由出自 `_survey_org_model.md` §F.3（151 条逐条理由 + 岗位 + 责任名俱全）。**
> A = 算法可作主引擎（全库 73 条，本 FLOW **28** 条）；B = 需补外部证据后匹配（全库 66 条，本 FLOW **8** 条）。
>
> 🔢 **本 FLOW 的 A 占比是三条 FLOW 里最高的**：28/36 = **77.8%**
> （FLOW-01 40/54 = 74.1%；FLOW-02 29/73 = 39.7%）。
> 这与 FLOW-02 形成鲜明对照 —— **「补货采购与交付」比「新品验证」可算法化得多**，
> 因为前者的对象（库存、提前期、产能、现金）是结构化量，后者的对象（用户愿不愿意买）不是。
> 这个结论是**从三批的数字算出来的**，不是印象。
>
> ⚠️ 其中 **4 条是本 FLOW 的 §F.5「A 类边界条目」**，A 身份**随阈值动摇**：
> `供应商评估`（A）· `履约跟踪`（A）· `到货异常追踪`（A）· `产能调查`（**§F.5 记 A、§F.3 判 B**）。
>
> 🔴 **材料内部矛盾（登记，不重判）**：`产能调查` 在 §F.5 的表头写「本次计入 A」，
> 而 §F.3 逐条判定 / §F.4 清单**均判 B**。处置：**以 §F.3 为准 ⇒ 按 B 处理**，
> 且**不得**把它计进「靶区一」（靶区一是按「A ∩ 无精选卡」定义的）。
> 这条矛盾**同时落在 FLOW-02 与 FLOW-03 两批上**，所以两个方案域的边界条目计数都会受它影响：
> **本 FLOW 的 4 条边界条目里只有 3 条是 A。**

## 4 方法从哪来（卡 ↔ 契约）

**契约按「责任」建，不按「卡」建**：一个责任的同族方法卡可以互换，换卡只换方法实现，
数据要求、标定规则与冻结条件不变。因此每份契约的 `cards` 只写 1–3 张**代表卡**。

### 4.1 两条卡语料与它们在**本 FLOW** 上的两个口径（**不要混算**）

| 线 | 事实源 | 规模 | 契约怎么用它 |
|---|---|---|---|
| **已装线**（消费口） | `dsh-paper2skills/data/classification.json` | 1338 张 | `cards` 优先写它的 **slug** —— S12 的预设白名单认这个键 |

| **契约口径** | 「方法可以从哪些卡来」= 已装线 ∪ 精选线 | **可写 35 / 待卡 1**（A 28 / B 7 可写，A 0 / B 1 待卡）|

## 6 停止条件与冻结（本 FLOW 的判据面）

**STG-06 Assurance 接收门禁七项检查**（逐字取自格定义，逐项可判定；**缺项即 HOLD，不设「部分通过」档**）：

1. **重复订单**（这张采购/调拨单是不是已有在途或已在系统里？）
2. **MOQ**（最小起订量是否满足）
3. **产能**（供应商/产线能不能吃得下）
4. **现金**（AGT-041 的资金与成本约束判定）
5. **质量**（AGT-018 的质量与在制状态）
6. **合同**（采购条款与既有承诺）
7. **对象状态**（账号/SKU/仓库/供应商是否处于可用状态）

> 🔢 七项 vs FLOW-01 的六项、FLOW-02 的五项：三条 FLOW 的判据面**确实不同**，
> 本条的独立项是 **重复订单 · MOQ · 产能 · 合同** —— 四项都指向同一件事：
> **采购是「先查再买」，不是「算出就买」**。
