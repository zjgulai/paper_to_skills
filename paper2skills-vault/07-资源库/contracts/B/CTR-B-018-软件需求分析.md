# 软件需求分析 · 供给契约

> **本契约的两部分，用法不同。** §1 / §2 / §3 / §5 / §6 是**作业口径** —— 据此产出方案：可达段给算式与取值，
> 不可达段给替代路径。§4 是**放行判据** —— 它规定的是「什么条件下不许自动走」，**不得整句抄成交付物的内容**。
>
> 本责任的判定理由（`_survey_org_model.md` §F.3）：需求歧义与一致性可 NLP / 形式化辅助，但**需求确认依赖业务与架构判断**。
> 这句话就是本契约可达段与不可达段的分界线 —— **机检能判「这句话写全了没有、和别的条目打不打架、变了会牵动谁」，
> 判不了「这个需求该不该做、这么做架构撑不撑得住」。**
>
> 岗位 AGT-012 软件算法与应用生态（DOM-02 / PLN-OPS），岗位产物「软件方案与验证证据」，
> 结果指标「用户任务成功与软件质量」；适用 FLOW-02 新品需求到商业验证、FLOW-07 重大质量与账号事件。
>
> **本契约覆盖的格**：方法格 = FLOW-02/STG-04、FLOW-02/STG-05、FLOW-02/STG-08、FLOW-07/STG-04、FLOW-07/STG-05、FLOW-07/STG-08
> （§1 的四个算式落在这些格上）；规则格 = 两跳各自的 STG-01／STG-02／STG-03／STG-06（Assurance 接收门禁）／STG-07（受控动作），
> **这些格只放判据与门禁条件，不挂载任何判别式**（§4 的落脚处）。
>
> **取值来源纪律（全文适用）**：本契约出现的每一个阈值、比例与时限，来源只有三种 ——
> （a）业务处境或材料已给出的数（出海历史 **2 个完整年度**＝决策 Q11；经营节奏「月度经营复盘」＝**1** 个自然月；
> 阶段边界 STG-01…STG-08）；（b）业务侧默认（经营者自述或行业惯例，逐条附替换条件）；（c）§1 算式由命名数据系统直出。
> **本责任没有候选卡，因此不存在卡面或论文数字可移植** —— 这一点写在 §1 开头，也是本契约与 A 类契约在结构上的唯一差别。

## 1 算法可达部分

- **候选卡状态（先读这一条再用本段）**：本责任的候选方法卡**为 0 张** —— 已装线（产品侧 1338 张）与精选线（146 张）两条卡语料里，都没有落在「软件需求分析」这一 L3 上的卡。**本责任暂无候选方法卡，这就是缺口账里的一条扩充工单**：需要认领「需求条目结构化 ＋ 歧义与一致性校验 ＋ 可追溯性」这一族的方法卡；认领后只替换方法实现，本契约的数据要求、标定规则与冻结条件不变。因此本段的四个算式是**本业务自己写死的判据**，取值全部来自下方逐条注明的业务侧默认与命名数据源，**没有卡面数字可列、无论文实验参数可引**（**不编**，也不拿别的责任的卡来顶）。
- **可达段一（需求条目的完备性机检）**：把每条软件需求拆成**五槽位** —— 主体（哪个对象或哪个岗位用）、动作（系统做什么）、对象（对哪个数据、接口或设备）、条件（在什么触发与边界下）、**可度量验收值**（拿哪个字段、到什么数算通过）；缺任一槽位判「不完整」，输出不完备条目清单，写入 FLOW-02/STG-04 的〈机会与可行性诊断〉软件侧证据栏与 FLOW-07/STG-04 的〈事件范围与根因诊断〉软件侧栏。
- 可达段一算式：`需求完备率 = 五槽位齐备的条目数 ÷ 需求条目总数`；源字段：〈需求条目台账〉的 `req_id`、`subject`、`action`、`object`、`condition`、`acceptance_field`、`acceptance_value`。
- 取值：**需求完备率 = 1.000（即 100%）**，等价于**不完备条目 = 0 条**才允许提交需求确认；该门限是**二值**的、不设部分通过档（**业务侧默认**，来源＝经营者自述「说不清拿什么判通过的需求，不上评审」）。**替换条件**：〈需求条目台账〉接入并覆盖满 **2 个完整年度**（决策 Q11）后，改用**实测**完备率与实测缺槽位分布重算；替换前该结论只能表述为「**未检出**不完备条目」，**不得**表述为「需求已完备」。
- **可达段二（条目之间的冲突与重复机检）**：在同一 `object` ＋ `acceptance_field` 上比对取值域，取互斥的两两组合；再按文本相似度归并语义重复的条目，输出冲突条目对与重复条目数。
- 可达段二算式：`冲突条目对数 = count(同 object 同 acceptance_field 上取值域互斥的条目对)`；`重复条目数 = 需求条目总数 − 归并后条目数`；归并按 `相似度(条目文本) ≥ 归并阈值` 判同一条。
- 取值：**冲突条目对数 = 0 对**、**重复条目数 = 0 条**（**业务侧默认**，来源同可达段一）；归并阈值 = **文本相似度 0.85**（**业务侧默认**，来源＝行业惯例的近似重复阈值）。**替换条件**：本司需求评审记录中「人工判定的其实是一条」的结论积累满 **20** 例后，归并阈值改用该 **20** 例中最小的真重复相似度；替换前归并结果**只作提示、不作删除依据**（疑似重复的条目一律保留原编号，由评审处置）。
- **可达段三（需求的可追溯性覆盖）**：每条需求必须链到「验收用例 ＋ 验收数据字段 ＋ 责任岗位」三元组，输出追溯覆盖率与悬空引用数，作为 FLOW-02/STG-05 的〈新品验证证据包〉中软件侧验收判据的完整性证据。
- 可达段三算式：`追溯覆盖率 = 三元组齐备的条目数 ÷ 需求条目总数`；`悬空引用数 = count(引用的用例或字段在台账中不存在的引用)`。
- 取值：**追溯覆盖率 = 1.000（即 100%）**、**悬空引用数 = 0 条**（**业务侧默认**）。**替换条件**：需求条目与验收用例在同一台账内落库并跑满 **2 个完整年度**后改用实测值；替换前追溯矩阵只用于本 Case 内的范围确认，**不得**作为验收完成率或交付质量的对外口径。
- **可达段四（变更影响闭包）**：需求条目变更时算出下游受影响集合与未闭合引用数，作为范围与停止条件的复核输入，写入 FLOW-02/STG-05 与 FLOW-07/STG-05 的方案段。
- 可达段四算式：`影响闭包 = { x : x 引用了本次变更条目 } ∪ { x : x 的验收字段取自本次被变更的字段 }`；`未闭合引用数 = count(引用指向已废弃条目的活条目)`。
- 取值：**未闭合引用数 = 0 条**（**业务侧默认**）；影响闭包按 `req_id` 去重后取 **1** 个集合、不分档。**替换条件**：〈需求条目台账〉接入后改用实测闭包；替换前影响闭包只用于提示复核范围，**不得**用于工期、人力或版本发布承诺。
- **本段的能力边界**：只做四件事 —— 条目是否完备、条目之间是否冲突或重复、条目能否追溯到验收、变更牵动多大范围；**不产出需求确认、不产出架构与实现可行性结论、不产出工期与版本承诺、不产出任何外部动作**（见 §2 各条）。
- **本段取值的来源逐条登记（供复核，缺卡也不留白）**：① 四个二值门限（完备率、冲突条目对数、追溯覆盖率、悬空引用数、未闭合引用数）＝**业务侧默认**，来源为经营者自述与 STG-06 接收门禁的二值口径；② 归并阈值 **0.85** 与复核样本 **20** 例＝**业务侧默认**，来源为行业惯例与经营者自述；③ 表内其余数字为 §1 算式在本司命名数据源上的输出。**三张候选卡都不存在，故本条不是「不得移植清单」而是「无来源可移植」的登记** —— 待本责任的扩充工单认领到方法卡后，该卡的案例数值同样逐条列入本契约的不得移植清单。
- 本契约对同族方法卡通用；换卡时只替换方法实现，其余要求不变。

## 2 不可达部分

- 不可达①（需**人的专业判断 ＋ 治理签署**）—— 需求确认本身：这条需求该不该做、验收值定多少算合理、哪一方说了算，属业务方的接受与范围裁决；本层只能证明条目写全了、没打架、可追溯。
  → 替代路径：由 AGT-009 产品定义与商业立项在 FLOW-02/STG-05 方案定稿前确认需求与验收判据、由 AGT-008 产品组合与新品孵化在 FLOW-02/STG-02 前给出范围基线与停止条件；补不上时先出「机检候选 ＋ 待确认」双栏交付并逐条标「待确认」，候选栏不得写入〈FLOW-02 Assurance Decision〉的接受项；后果是该 Case 停在 FLOW-02/STG-06 接收门禁，不得发起受控外部验证。
- 不可达②（需**外部事实**）—— 架构与实现可行性：现网版本与依赖的真实状态、云资源与集成约束、平台侧接口的限流与政策原文，都在本司台账之外或在别岗手里，本层读不到权威副本。
  → 替代路径：由 AGT-012 本岗在 FLOW-02/STG-05 前出架构评估结论、由 AGT-047 系统集成与业务工具在装配 FLOW-02 Context Manifest 时提供〈接口契约〉与集成边界、由 AGT-027 店铺账号健康与规则在 FLOW-07/STG-04 收口前把平台政策原文连同生效版本号交来；补不上时退到「现网版本清单 ＋ 上一版架构基线」作初判，逐条挂「未评审」；缺了它，涉跨系统字段的需求落不到具体的集成边界上，本 Case 的验收字段也就悬着。架构评估结论与〈接口契约〉补齐后整批替换；在此之前这类需求只能留在候选栏，进不了验证意图
- 不可达③（需**实物或回执**）—— 软件侧的真实性验收：设备连接与固件版本回执、真机环境下的实测结果、事件场景的回放日志，本层只能读到自己写的用例，读不到外部实测。
  → 替代路径：由 AGT-013 产品验证与研发项目在 FLOW-02/STG-08 关闭前出测试报告与固件版本回执、由 AGT-049 Agent平台与可靠运行在 FLOW-07/STG-08 关闭前出运行日志与回放记录；补不上时把自测日志与版本号先当过程证据用，逐条挂「回执未齐」；缺了它，「在真机跑过」这件事只有自己写的用例作证，软件侧的验证结论就成了自证。测试报告与固件回执补齐后整批替换；在此之前两跳的关闭栏只写「未闭合」并留观察窗
- 不可达④（需**治理签署**）—— 需求歧义的最终裁量：同一句需求被两个业务方读成两件事，或两条需求抢同一份资源时，谁优先属治理裁决；本层只能把冲突列出来。
  → 替代路径：由 AGT-008 产品组合与新品孵化在 FLOW-02/STG-02 建单前给出范围基线、由 AGT-001 经营目标与资源统筹在两方诉求冲突时于 FLOW-02/STG-06 前裁决优先级；补不上时先按〈新品验证 Case Charter〉已写明的范围与停止条件顶替，冲突项统一进「待裁决」栏并标注，后果是该需求不进本期范围，也不计入本期需求的完备率分母。
- 不可达⑤（需**外部事实 ＋ 法定签署**）—— 上架与合规类软件事实：应用或固件随新品出海涉及的安全、隐私与合规要求（个人数据最小化、儿童数据、平台对软件功能的规定），其判定权在法定与合规侧。
  → 替代路径：由 AGT-044 产品合规与隐私在 FLOW-02/STG-05 前出具适用性判读、由 AGT-043 法务与知识产权出宣称边界意见、由 AGT-050 信息安全与权限在 FLOW-02/STG-06 前确认取数与账号权限；补不上时先拿平台公开文档截图与上一版已生效的版本号凑合，逐条挂「未核验」；缺了它，涉隐私与上架的验收判据没有可引的权威文本，本 Case 也无法从候选栏走到受控动作。合规判读与法律意见到位后整批替换；在此之前这类需求一律只记意图并转人工工单

## 4 该格何时必须冻结

- 需求完备率 < 1.000（存在不完备条目）而拟将该批需求提交确认或形成验证 Intent ⇒ 该格不得推进到 FLOW-02/STG-07 受控动作，只能形成 NoActionRecord。
- 冲突条目对数 > 0 对而未指定裁决方 ⇒ 冻结该 Case 的需求范围，回 FLOW-02/STG-02 重定范围基线与停止条件，不得进入方案阶段。
- 追溯覆盖率 < 1.000（有需求未链到验收用例、验收字段与责任岗位）或悬空引用数 > 0 条 ⇒ 该批需求不得写入〈新品验证证据包〉的验收判据，只作候选。
- 需求确认（AGT-009）或范围基线（AGT-008）缺位，而拟动作是验证 Intent、软件侧处置或恢复动作 ⇒ 该 Case 的 Assurance Decision 判 HOLD，转人工。
- 架构与实现可行性未经 AGT-012 本岗评审，或〈接口契约〉（AGT-047）未给出而拟动作依赖跨系统字段 ⇒ 相关需求不得进入受控动作，只能出候选 ＋ 人工工单。
- 涉个人数据、儿童数据或平台软件功能规定的需求未经 AGT-044 适用性判读，或对外表述无 AGT-043 法律意见 ⇒ 不得进入受控动作，相关条目停在候选栏。
- AGT-050 未提供取数权限或账号责任人清单 ⇒ 该 Case 的 Assurance Decision 判 HOLD，不得取用未授权数据源。
- AGT-046 未给出数据来源标识或新鲜度，或证据新鲜度超出 §5 ④ 的快照要求 ⇒ 该批数据不进入机检分母，该 Case 冻结在 STG-04。
- 需求条目在本 Case 关闭前被变更而未重算影响闭包 ⇒ 该 Case 不得关闭；未闭合引用数 > 0 条时不得把软件侧结论判为「已验证」。
- 同一对象在当周内已有一次未回填的验证 Intent 或处置尝试 ⇒ 不得对同一对象发起新动作；**已成功动作不得随整单重跑**。
- 自 FLOW-02/STG-05 或 FLOW-07/STG-05 的产物提交起，至该 Case Charter 已写明的观察窗截止日仍未取得 §3 所列任一项证据 ⇒ 判 HOLD 并转人工，不得默认放行。

## 5 数据要求（五维 · 三列）

| 维 | 取值 | 缺值处置（**取值为缺口时必填**：先用什么顶替 + 什么条件下换成什么） |
|---|---|---|
| ① 获取路径 | 自有埋点（Case/Event Ledger 的 Case Charter、阶段接收记录与动作记录）＋平台后台（应用与账号后台的版本、政策通知）＋需授权（〈接口契约〉、现网版本清单、取数权限清单） | 非缺口。若某类需求来自线下评审（会议纪要、邮件、群内口头提出）：本维取不到，先按〈新品验证 Case Charter〉的人工备注与纪要附件顶替并标「非留痕」；该类需求纳管进〈需求条目台账〉后替换为条目级记录，替换前不计入完备率分母，也不得据其判需求优先级 |
| ② 粒度 | 一条 = 一条软件需求条目（含五槽位、验收字段与验收值），按 `req_id` × 目标版本 × 对象组织；追溯侧到「条目 × 验收用例 × 字段 × 责任岗位」四元组 | 非缺口。若某批需求只以「模块」为单位登记、无法拆到条目级：先按模块粒度顶替并把该批标「粒度不足、不作完备率判定」，该批只出提示；条目级台账到位后替换，替换前该批不得进入 §4 的冻结判定 |
| ③ 回溯深度 | 近 2 个完整年度（业务处境给出的出海历史长度，决策 Q11），用于算需求的触发频次与历史变更影响 | 非缺口。某产品线或某系统在本司上线还不满两年时：把它从上线首月起的条目与变更记录整段拿来当窗口，注明「样本不足」，这一段只出趋势提示与候选。缺了它，§1 可达段一的完备率会拿一个还没走完年度的台账当实测基准，看着高只是因为条目没攒够。该线上满两年后整段替换为完整窗；替换前这段不得用来定需求优先级 |
| ④ 新鲜度 | 每次进入 FLOW-02/STG-04 或 FLOW-07/STG-04 前重读一次；需求条目与验收字段的变更实时落账（当日可查）；进入 STG-06 接收门禁前须为「截至前一日 24:00」的完整快照 | 非缺口。台账按离线批量 T+1 落库、当天查不到时：把当日的评审纪要与变更申请单拿来先顶，只用来判「这条需求今天在不在」，并给每条挂「口径非权威」；没有当日可读的活条目时，§1 可达段四的未闭合引用数就失去底稿，影响闭包可能算的是昨天那一份。台账做到当日可查后整段替换；在此之前不得关闭 Case，也不得判「影响闭包已核清」 |
| ⑤ 口径归属 | AGT-045 指标契约与主数据（需求条目的编号与状态、验收字段的分子分母与时间归属、责任岗位的归属规则）—— 其中「用户任务成功与软件质量」这一结果指标的**口径尚未由 AGT-045 定名**（判定字段、权重与时间归属都未定），缺它算不出跨版本的软件质量可比性，同一句「任务成功」在两个版本里可以指着两个不同字段；每条记录随带 AGT-046 的质量状态、来源与新鲜度 | **先按**本 Case 的〈新品验证 Case Charter〉已写明的验收判据与停止条件**暂按**单版本口径，并逐条标注「口径未签发」；AGT-045 签发该结果指标口径后**替换**为权威字段与权重；替换前该指标只在本 Case 内用于判「继续 / 转向 / 停止」，**不得**跨版本、跨品类比较，也不得对外表述为软件质量水平 |
